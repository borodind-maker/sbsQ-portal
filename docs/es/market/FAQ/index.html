    SmartBees Quantum (sbsQ) - Objections & Answers

    Document Type: Sales Enablement
    Version: 1.0
    Last Updated: 2026-01-14
    Classification: Business Confidential

    Technical Questions

    Q1: Is this "just another AI"?

    A: No. sbsQ is not an AI model—it's a policy verification layer that constrains AI with physics and statistics.

    Analogy: Think of it like a compiler's type checker for AI claims. The LLM can propose anything, but sbsQ only accepts what's physically consistent with sensor measurements.

    Key Difference: - Traditional AI: "I think the obstacle is 15m away" → system acts on it - sbsQ: "I think the obstacle is 15m away" → gate checks against sensors → if residual is too large, REJECT → safe mode

    Q2: What if the sensors are lying (spoofed/faulty)?

    A: This is exactly what sbsQ is designed to detect.

    How: 1. Multi-sensor cross-validation: If GNSS says 10m but vision says 15m, the residual is large → UNKNOWN or REJECT 2. Statistical outlier detection: Spoofed data typically creates large z-scores (beyond normal sensor noise) 3. Temporal consistency: Sudden jumps (e.g., position teleports 100m) fail gate verification 4. Calibration loop: If a sensor consistently produces high residuals, it's flagged for recalibration or exclusion

    Outcome: sbsQ doesn't "trust" sensors blindly—it verifies consistency across modalities and time.

    Q3: Won't this create too many REJECT decisions (false positives)?

    A: Not if calibrated properly. This is why we have mode-specific thresholds and sensor profiling.

    Example: - Cruise mode: Relaxed thresholds (z < 2.5) → fewer REJECTs, prioritize efficiency - Precision mode (landing): Strict thresholds (z < 1.5) → more REJECTs, prioritize safety

    Calibration process: 1. Collect ground-truth data (RTK GNSS, mo-cap, surveyed landmarks) 2. Measure empirical sensor noise (σ_meas, σ_pred) 3. Tune thresholds to achieve target FPR (e.g., < 5%)

    In practice: Pilots show REJECT rates of 2–5% in normal conditions, 15–30% under active degradation (which is correct behavior).

    Q4: How does this work with existing autonomy stacks?

    A: sbsQ is designed as a drop-in layer, not a replacement.

    Integration points: - Input: Hypotheses from LLM/VLG or high-level planner - Sensor interface: Queries existing estimators (EKF, SLAM, trackers) - Output: ACCEPT/UNKNOWN/REJECT decision + rationale

    Supported platforms: - ROS / ROS 2 - PX4 / ArduPilot - Custom autonomy stacks (via API)

    Typical integration time: 1–2 weeks for reference platforms, 4–8 weeks for custom stacks.

    Q5: What's the computational overhead?

    A: Minimal. Gate computation is < 10ms on typical edge hardware.

    Breakdown: - 1D gate (z-score): < 1ms - Multi-D gate (χ²): < 5ms (for ν ≤ 9) - Hypothesis parsing: < 5ms - Total: < 20ms end-to-end

    Hardware requirements: - CPU: Single core @ 1GHz - Memory: < 50MB - Tested on: Raspberry Pi 4, NVIDIA Jetson Nano, Intel NUC

    Impact on control loop: Negligible (control loops typically run at 10–50Hz, gate adds < 20ms).

    Business Questions

    Q6: Why should I pay for this when I can build it myself?

    A: You could, but consider:

    Time to market: - DIY: 6–12 months of R&D + validation - sbsQ: 1–2 weeks integration, 4–8 weeks pilot

    Expertise required: - DIY: Statistical verification, sensor fusion, LLM integration, compliance artifacts - sbsQ: We've already solved these problems (validated in 1M+ test cycles)

    Ongoing maintenance: - DIY: Your team maintains, updates, supports - sbsQ: We handle updates, bug fixes, new features

    Compliance: - DIY: Build your own Safety Case from scratch - sbsQ: Pre-built templates, audit artifacts, certification support

    ROI: Most customers see payback in < 2 months (incident cost reduction).

    Q7: What if sbsQ becomes a single point of failure?

    A: sbsQ is designed with fail-safe defaults.

    Failure modes: 1. sbsQ module crashes: System reverts to baseline behavior (with optional safe mode) 2. All sensors degraded: UNKNOWN decision → request operator intervention (not "guess and crash") 3. Gate computation error: Conservative fallback (REJECT → safe mode)

    Redundancy options: - Run sbsQ on redundant compute (primary + backup) - Watchdog monitoring (restart on failure) - Graceful degradation (disable sbsQ, log incident, continue with reduced autonomy)

    In practice: sbsQ reduces single points of failure by catching sensor/AI errors before they propagate.

    Q8: How do you handle edge cases / unknown unknowns?

    A: This is where UNKNOWN is powerful.

    Philosophy: It's better to say "I don't know" than to guess wrong.

    Example: - Sensor data is ambiguous (high uncertainty) - Multi-sensor conflict (no clear winner) - Novel scenario (outside calibration envelope)

    sbsQ response: 1. Decision: UNKNOWN 2. Action: Trigger diagnostic policy (re-measure, alternate sensor, peer check, operator query) 3. LLM mode: Entropy Starvation (reduce temperature, force structured diagnostic output)

    Outcome: System doesn't hallucinate a solution—it asks for better data or human input.

    Q9: What about regulatory compliance (DO-178C, ISO 26262, etc.)?

    A: sbsQ is designed to enable compliance, not complicate it.

    Compliance-friendly features: 1. Deterministic verification: Gate logic is explainable, auditable, repeatable 2. Audit artifacts: Every decision logged with residuals, thresholds, sensor IDs, timestamps 3. Replay capability: Reconstruct any incident from logs (required for certification) 4. Safety Case templates: Pre-built argument structures for common standards

    Certification support (Enterprise package): - DO-178C templates (aviation) - ISO 26262 templates (automotive) - MIL-STD-882E (defense) - Liaison with certification bodies

    Customer feedback: "sbsQ turned our compliance nightmare into a checklist."

    Competitive Questions

    Q10: How is this different from [Competitor X]?

    A: Most competitors fall into one of three categories:

    1. AI-only safety monitors (e.g., runtime verification for neural networks)

    • What they do: Monitor AI outputs for anomalies (pattern-based)
    • Limitation: No physics grounding—can't detect plausible but wrong outputs
    • sbsQ advantage: Physics-statistical verification (not just pattern matching)

    2. Sensor fusion platforms (e.g., advanced Kalman filters)

    • What they do: Combine sensor data to estimate state
    • Limitation: Brittle under adversarial conditions (spoofing, jamming)
    • sbsQ advantage: Ternary logic (UNKNOWN is a safe state), policy-based degradation

    3. Rule-based safety systems (e.g., geofencing, speed limits)

    • What they do: Hard-coded constraints
    • Limitation: Poor generalization, can't handle novel scenarios
    • sbsQ advantage: AI flexibility + physics constraints (best of both worlds)

    Unique position: sbsQ is the only platform that makes AI prove its claims with physics before acting.

    Q11: Can't I just use better sensors?

    A: Better sensors help, but they don't solve the fundamental problem.

    Why: 1. All sensors degrade: Even RTK GNSS fails indoors, vision fails in low light, magnetometers saturate near EMI 2. Adversarial environments: Jamming/spoofing affects even high-end sensors 3. Multi-sensor conflicts: Better sensors can still disagree (e.g., GNSS vs vision in urban canyons)

    sbsQ value: Works with any sensor quality—it's about verifying consistency, not replacing sensors.

    Analogy: Better sensors = better data. sbsQ = verifying the data is trustworthy before acting on it.

    Q12: Why is the pricing per-device / per-fleet?

    A: Because value scales with deployment size.

    Rationale: - Per-device: Fair for small deployments (pay for what you use) - Per-fleet/per-site: Predictable cost for large deployments (no surprise bills)

    Volume discounts: 10–50% off for 25+ devices (see pricing packages).

    Alternative: Enterprise customers can negotiate custom terms (e.g., unlimited devices, multi-year).

    Q13: What happens if we exceed our device limit?

    A: Automatic upgrade to the next tier (or per-device billing, whichever is more cost-effective).

    Example: - You have Pro (up to 25 devices) at $75K/year - You deploy device #26 - Options: - Upgrade to Enterprise ($250K/year, unlimited devices) - Pay per-device ($2,500/device/year for devices 26+) - We choose the cheaper option for you (in this case, per-device until you hit ~95 devices)

    No surprise bills: We notify you before auto-upgrade, you can adjust deployment if needed.

    Q14: Can we start with a pilot and upgrade later?

    A: Yes! This is our recommended path.

    Pilot → License pathway: 1. Pilot (4–8 weeks): Fixed fee ($25K–$150K depending on scope) 2. Results: Measurable outcomes (FP/FN, recovery time, safety) 3. Decision: Proceed to license or not 4. Credit: 20–50% of pilot fee credited toward first-year license (depending on package)

    Why pilots work: - Low risk (fixed cost, defined scope) - Measurable proof (not just promises) - Hands-on experience (your team learns the tech)

    Conversion rate: 80%+ of pilots convert to licenses (because the metrics speak for themselves).

    Implementation Questions

    Q15: How long does integration take?

    A: Depends on your platform:

    Platform Integration Time Notes
    ROS / ROS 2 1–2 weeks Reference implementation available
    PX4 / ArduPilot 2–4 weeks Adapter in beta, requires companion computer
    Custom stack 4–8 weeks Depends on estimator interface complexity

    What you need: - Access to sensor estimates (EKF/SLAM/tracker outputs) - Ability to intercept/gate high-level commands - Compute resource for sbsQ module (minimal: Raspberry Pi 4)

    Support: We provide integration assistance (included in Pro/Enterprise, optional for Base).

    Q16: Do we need to retrain our AI models?

    A: No. sbsQ works with any LLM/VLG without retraining.

    How: - sbsQ operates downstream of the AI model - AI generates hypotheses (as usual) - sbsQ verifies them (new layer) - No changes to model architecture, training, or inference

    Bonus: Entropy Starvation mode actually improves LLM behavior over time (it learns to be more cautious when uncertain).

    Q17: What if our operational environment changes?

    A: sbsQ is designed for adaptive calibration.

    Scenarios: 1. New sensor added: Profile it (collect ground-truth data, measure σ), add to config 2. New operational mode: Define thresholds (e.g., "night mode" with relaxed vision thresholds) 3. Environmental shift: Recalibrate (e.g., moving from desert to urban, different GNSS/vision characteristics)

    Tooling: - Calibration toolkit (offline: batch processing of logs) - Online adaptation (advanced, Phase 2): Auto-adjust σ based on recent performance

    Typical recalibration: 1–2 days of data collection + analysis.
